# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Monorepo nominally managed with **deno** workspaces (`deno.json` lists workspace
members), but that workspace list (`apps/example-app`, `packages/example-lib`) is
still a placeholder — neither directory exists. `packages/` is empty.

- `apps/` — deployable applications.
  - `apps/docs-webapp-with-fumadocs/` — the one real app so far, a TanStack
    Start + Fumadocs documentation site. It is **not** a deno workspace
    member: it's an npm/vite-managed app with its own lint/type-check tooling,
    and is explicitly excluded from root `deno lint`/`deno fmt` in
    `deno.json` (its TanStack-generated `src/routeTree.gen.ts` doesn't pass
    deno's lint rules and shouldn't be hand-edited to fix that).
- `packages/` — shared libraries consumed by apps (and each other). Empty.
- `adr/` — architecture decision records (ADRs). Not `docs/adr` — that was
  deliberately moved so `docs/` is free for documentation site content.
- `docs/` — reserved directory for documentation site content/build output;
  currently empty. Not to be confused with `apps/docs-webapp-with-fumadocs`,
  which is the app that will render that content.

## Commands

Root (deno):

```bash
deno install       # install dependencies
deno lint           # lint (run in CI)
deno test -A        # run tests (run in CI)
```

To run a single test file: `deno test -A path/to/file_test.ts`. Note: with no
deno workspace members or test files yet, both `deno lint` and `deno test -A`
currently have nothing to check at the root — this is expected until a real
deno-based app/package is added under `apps/`/`packages/`.

`apps/docs-webapp-with-fumadocs` (npm-managed — run from inside that
directory):

```bash
npm install
npm run dev          # vite dev server, http://localhost:3000
npm run build
npm run start         # serve built .output/public (uses ../../serve.json)
npm run lint          # oxlint
npm run types:check   # tsc --noEmit
```

## Architecture: `apps/docs-webapp-with-fumadocs`

TanStack Start (React) app generated via `create-fumadocs`, using Fumadocs
for MDX content, docs layout, and search. Everything hangs off one shared
`source` object built in `src/lib/source.ts` (`defineDocs` + `loader` from
`fumadocs-core/source`, reading MDX from `content/docs/`); several routes
each consume it independently:

- `src/routes/docs/$.tsx` — catch-all doc page. A `createServerFn` loader
  resolves the requested page from `source`, serializes the page tree, and
  the component renders the MDX body via `fumadocs-ui`'s `DocsPage`.
- `src/routes/api/search.ts` — search endpoint built from `source` via
  `fumadocs-core/search/server` (Orama, English).
- `src/routes/llms[.]txt.ts` / `llms-full[.]txt.ts` — plain-text dumps of the
  docs for LLM consumption, built from `docsLlms` (also derived from
  `source` in `src/lib/source.ts`).

Routing is TanStack Start's file-based routing; `src/routeTree.gen.ts` is
auto-generated by the TanStack Router plugin — don't hand-edit it, and
regenerate by running `dev`/`build` rather than fixing it manually if it
looks stale.

`vite.config.ts` wires together the `fumadocsMdx`, `tailwindcss`,
`tanstackStart` (which also declares the static/prerendered `pages` list),
`react`, and `nitro` vite plugins — check this file first when adding a new
top-level route or static page.

## Workflow requirements (from AGENTS.md)

- Read the relevant `README.md` for the package/app you're touching before
  making changes, and check open issues for related, in-progress work.
- For anything non-trivial (new component, cross-cutting change, architecture
  decision), write a short ADR under `adr/` **before** writing code — copy
  `adr/TEMPLATE.md` to `adr/adr-NNN-short-slug.md` (next free number). Skip it
  for anything easily changed later.
- Create a branch per issue/feature; never commit directly to `main`.
- Match existing code style/conventions in the file or package being edited
  rather than introducing a new pattern.
- Add or update tests for behavior you change.
- Run the lint/test commands in the package's `README.md` before opening a
  pull request.
- Fill in the PR template, including a link to the issue it closes. Don't
  merge your own PR; wait for review unless explicitly told otherwise.
- Don't add dependencies without checking if an existing one already covers
  the need.
- Don't rewrite or reformat files that aren't otherwise being changed.
- Don't remove tests to make CI pass — fix the underlying issue.
- Keep PRs/commits scoped to one logical change; unrelated cleanup belongs in
  a separate PR.
